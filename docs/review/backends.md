# CPU backend crates review rules

Read with `docs/review/REVIEW.md`; this file adds the rules specific to the CPU backend crates (`poulpy-cpu-portable`, `poulpy-cpu-avx`, `poulpy-cpu-avx512`, `poulpy-cpu-arm`, `poulpy-cpu-rayon`, `poulpy-cpu-oracle`).

## 0. Scope and terms

- **Terms.** *Twin* and *base*: a Rayon twin and the serial type it schedules (`docs/review/workspace.md` section 12.2); *CI form*: a type's conjugate-invariant instantiation; *word family*: `fft64` (`BigWord = i64`) or `ntt4x30` (`BigWord = i128`); *packed* NTT4x30 domain: the `CrtWord<Primes30, u32>` layout of `poulpy_cpu_portable::ntt4x30`.

## 1. Crate roles and dependencies

Generic rule: `docs/review/workspace.md` section 1 (dependency direction).

- **Portable defines the plumbing.** poulpy-cpu-portable depends on no other `poulpy-cpu-*` crate (the oracle only in `[dev-dependencies]`) and alone defines the `hal_defaults` traits, the `hal_impl_*!` binding macros, the registration macros (`impl_cpu_core_defaults!`, `impl_cpu_ckks_defaults!`, `impl_sampling_host!`, `impl_ckks_encoding!`, `impl_ckks_paco_coeff_encoding!`, `impl_ckks_ship_coeff_encoding!`), the shared CPU test suites and helpers (`kernels::SendPtr`, `kernels::with_thread_buffer`, `hal_defaults::take_host_typed`, `ntt4x30::drivers`), and a helper a second CPU crate needs moves there as `#[doc(hidden)] pub` with a CHANGELOG entry.
- **Rayon sits on portable.** poulpy-cpu-rayon holds all code needing both portable kernels and Rayon and takes poulpy-core and each scheme crate only behind its `enable-*` feature, which also enables that poulpy-cpu-portable feature where twins register through a portable macro, and its exported macros reach `rayon`, `bytemuck`, `poulpy_hal` and `poulpy_cpu_portable` through `$crate::__private`.
- **SIMD crate dependencies.** A SIMD crate takes poulpy-hal, poulpy-core and poulpy-cpu-portable unconditionally and each scheme crate only behind its feature, schedules on Rayon only through poulpy-cpu-rayon, taken behind `enable-rayon` (a direct `rayon` dependency only for a used facility poulpy-cpu-rayon lacks, the IFMA per-cache thread pools), and takes the oracle, poulpy-bench and a sibling SIMD crate it attests against (poulpy-cpu-avx in poulpy-cpu-avx512, under `cfg(target_arch = "x86_64")`) only in `[dev-dependencies]`.
- **The oracle shares nothing.** poulpy-cpu-oracle depends on poulpy-hal and, behind its features, the scheme crates it registers, never on another `poulpy-cpu-*` crate, and takes from the scheme crates only the reference and derived registration macros, the reference encoding circuit, contract definitions and constants (`Noise::gaussian_parts`, `CKKSFloat`, `ROOT_TABLE_LOG_ORDER`) and the controlled-sampling test helpers.
- **Modules built only by tuning.** Generic rule: `docs/review/workspace.md` section 2 (caller owns modules and scratch). Besides `HalModuleImpl::new`, library code builds a `Module` only in `poulpy_cpu_rayon::tuning::thread_scaling` (the `#[ignore]`d `tuning::thread_scaling_report` tests behind `enable-rayon`), which no operation reaches.

## 2. Backend types and names

Generic rule: `docs/review/workspace.md` section 12.

- **One marker per backend.** A CPU backend is one zero-sized `pub struct <Family><Isa>[Rayon]<R: Ring = Standard>(PhantomData<R>)` (the oracle: `Oracle<F, R>`) with `impl<R: Ring>` `Backend` and ring-generic kernel traits, a serial handle `<Backend>Handle` and the CI alias `pub type <Family>CI<Isa>[Rayon] = <Family><Isa>[Rayon]<ConjugateInvariant>;`, exported from `lib.rs` and documented ``/// [`<Family><Isa>[Rayon]`] over the conjugate invariant ring.``, a renamed type keeps a `#[deprecated(note = "renamed to ...")]` alias, and new code and docs use no deprecated alias (`FFT64Ref`, `NTT4x30Ref`).
- **Kernel names.** Exported kernels, compositions, table and plan builders and scratch queries of `poulpy_cpu_portable::kernels` end in `_portable`, one implementing a HAL operation carrying its name, a SIMD kernel swaps `_portable` for its crate's ISA suffix (`_avx2_fma` or `_ifma` only where it uses FMA or IFMA), no suffix naming an ISA the code does not use, a parallel driver ends in `_par`, and kernel trait methods keep their contract names.
- **Kernel and defaults traits.** A slice primitive is a kernel trait in `kernels::{znx, fft64::reim, fft64::reim4, ntt4x30}` named after its primary method with its `*_portable` function as default, grouped kernel families (`ReimArith`, `Reim4BlkMatVec`, `Reim4Convolution`, `I64Ops`, `I128BigOps`, `ZnxNormalize`) give every method a portable default, `hal_defaults` traits are `<Transform><Family>Default` (transform-independent: `HalVecZnxDefault`) with `<op>_default` methods, binding macros `hal_impl_<family>!` (split: `_without_normalize!`, `_normalize!`), and scheme macros `impl_cpu_<scheme>_defaults!`.
- **Defaults follow the word types.** A backend binds its word family's defaults (`FFT64*Default` and `fft64` for `BigWord = i64`, `NTT4x30VecZnxBigDefault` and `ntt4x30` for `BigWord = i128`, NTT3x42 included), and a method added to one word-family defaults trait enters every word-family trait of its OEP family with the same signature.

## 3. Assembly and registration

### 3.1. Files and new types

- **One file per layer.** Each layer registers in its root file (`hal_impl.rs`, `core_impl.rs`, `ckks_impl.rs`, `bin_fhe_impl.rs`, `mhe_impl.rs`, `blas_impl.rs`; the oracle: `hal.rs`, `core_impl.rs`, `ckks.rs`, `bin_fhe.rs`, `blas.rs`; poulpy-cpu-rayon's portable twins under `src/portable/`), plus, in poulpy-cpu-portable and a SIMD crate, `capabilities.rs` and, in a SIMD crate, `layout_compat.rs`, a new scheme in a new file behind `enable-<scheme>` (and, in a SIMD crate, the ISA feature).
- **New types reach every list.** A new backend type, its CI form and its twin each enter in the same PR every list selecting types, each mirroring portable's for the same ring: the `lib.rs` exports and README list, every layer file's families (a twin's HAL in its `rayon.rs`; `bin_fhe_impl.rs` for standard-ring types only), `capabilities.rs`, `layout_compat.rs` when its layout matches portable's (section 5.7), and the test registrations of section 13.
- **Capability entries.** Each SIMD type, CI and Rayon forms included, and each serial poulpy-cpu-portable type, CI forms included, has one `BackendCapability` (crate, enabling feature, target features, `compiled` from its `cfg!`) in its crate's capability list (`capabilities::portable_backends()`, a SIMD crate's `capabilities()`), a new instruction set adds an `instruction_sets()` entry and updates the test pinning their count, and `pub mod capabilities` compiles without the ISA feature, reporting `supported = false` off-target (`is_x86_feature_detected!` on x86, the target architecture alone on aarch64).

### 3.2. HAL families

Generic rule: `docs/review/workspace.md` section 3 (one family per layout, selection is explicit).

- **Every family on every type.** Every HAL OEP family is implemented for every backend type, serial, Rayon, both rings where it applies and the oracle (an empty `unsafe impl` where derived defaults suffice), and a new family or required method lands in the same PR in `poulpy-cpu-portable/src/hal_impl/bindings.rs`, every hand-written family (`poulpy-cpu-portable/src/ntt4x30/hal_impl.rs`, `poulpy-cpu-oracle/src/hal.rs`, the SIMD NTT families), each SIMD `hal_impl.rs` and Rayon file, the twin builders of `poulpy-cpu-rayon/src/fft64.rs` and `ntt4x30.rs` and, if ring-generic, `impl_fft64_delegating_backend!` (a standard-only family only when a registration on it needs it).
- **New HAL operations land whole.** A new CPU HAL operation brings its exported `*_portable` kernel (plus `*_tmp_bytes_portable` when it takes scratch), its `<op>_default` on each applicable word-family trait (or its method in `poulpy-cpu-portable/src/ntt4x30/hal_impl.rs` for a packed transform-domain family), its `hal_impl_*!` arm, an oracle body (section 9) and its registrations (section 13.2).
- **Standard-only families and split arms.** `HalVecZnxMonomialImpl` (`hal_impl_vec_znx_monomial!`) and `HalVecZnxCIImpl` (`hal_impl_vec_znx_ci!`) are implemented on the standard instantiation alone (`for FFT64Portable`, no ring parameter; `docs/review/hal.md` section 6), twins included, every other family once over `R: Ring` (or per ring where a twin macro builds per ring), a new required method goes into exactly one arm of `hal_impl_vec_znx!` or `hal_impl_vec_znx_big!`, the `_without_normalize!` one unless it normalizes, and a standard-only method into `hal_impl_vec_znx_monomial!` or `hal_impl_vec_znx_ci!`.
- **Binding arms forward only.** A `hal_impl_*!` arm is one forward to `<Self as $defaults>::<op>_default(module, ..)`, or the constant query of a scratch-free body, with no assertion, branch or arithmetic (as delegates, `docs/review/workspace.md` section 3).

### 3.3. Core and CKKS

Generic rules: `docs/review/core.md` section 1 (registration lists) and `docs/review/ckks.md` section 1 (register a new family everywhere).

- **Core registration.** Every production CPU type, CI and Rayon forms included, registers in `core_impl.rs` `impl_cpu_core_defaults!(BE, fft64 | ntt4x30)` (the `impl_core_reference_full!` families minus tensoring and the strided digit product, plus `impl_sampling_host!`) or its hand expansion, `GLWETensoringImpl` and `GGLWEProductDigitsStridedImpl` explicitly, and on standard-ring types the standard-only list of `poulpy-cpu-portable/src/core_impl.rs`.
- **CKKS registration.** Every CPU type calls `impl_cpu_ckks_defaults!` (the both-ring families plus `impl_ckks_encoding!`), each standard-ring type, twins included, adds the standard-only list of `poulpy-cpu-portable/src/ckks_impl.rs`, a CI form registers only the defaults, and a family some backend specializes (encapsulated ModUp, the encoding transform) is registered per type, never in a shared macro.
- **Hand-kept lists move together.** A new family enters in the same PR every list whose types need it: the shared macro or the standard lists of poulpy-cpu-portable, `poulpy-cpu-rayon/src/portable`, poulpy-cpu-avx, poulpy-cpu-avx512 (IFMA included) and poulpy-cpu-arm, the oracle's `impl_oracle_core[_standard]!` and `impl_oracle_ckks[_standard]!`, and the test fixtures using it (the ControlledSampling and DifferentSampling fixtures of `poulpy-cpu-portable/src/hal_impl/delegating_backend.rs`, the `poulpy-cpu-portable/src/ckks_comparison.rs` adapters, both for a both-ring family, `OverrideBackend` of `poulpy-cpu-portable/src/tests/ckks_overrides.rs`).
- **Overriding inside an umbrella.** A type overriding one family of an umbrella (`impl_cpu_core_defaults!`, a `*_reference_full!`) lists the other registrations individually in the same order, `impl_sampling_host!` included, beside the hand-written family, which forwards every method it does not specialize, queries included, to the public `*Reference` methods, and hand expansions gain new umbrella families in the same PR.

### 3.4. bin-fhe, mhe and blas

- **bin-fhe through `register_backend!`.** A standard-ring CPU type opts into bin-fhe only through the crate-local `register_backend!(Type, Comparison, bin_fhe_parity_<type>[, scheduling = parallel])` in `bin_fhe_impl.rs` (`Comparison` per section 3.5, twins passing `scheduling = parallel`), which expands `impl_bin_fhe_reference_full!` plus a `#[cfg(test)]` module with `bin_fhe_parity_test_suite!` against `Comparison` and `bin_fhe_reference_test_suite!`, the module keeping the `bin_fhe_parity_` prefix, and the oracle through a plain `impl_bin_fhe_reference_full!` on its two standard types.
- **mhe registration.** A crate selecting mhe has `enable-mhe = ["dep:poulpy-mhe", "enable-core"]` (a twin crate also forwarding its base crate's `enable-mhe`) and, behind it, an `mhe_impl.rs` pairing per type `poulpy_mhe::impl_mhe_reference_full!(crate::Type);` (or family macros plus hand-written impls) with `poulpy_mhe::mhe_backend_test_suite!(mod mhe_<type>, backend = crate::Type);` under `#[cfg(test)]`.
- **blas registration.** `enable-blas = ["dep:poulpy-blas", "enable-ckks"]` gates a `blas_impl.rs`, gated like `ckks_impl.rs`, selecting `::poulpy_blas::impl_blas_reference_full!(crate::<Type>)` for every type, CI, Rayon and IFMA types included under their features, or the other family macros plus a hand-written impl for an overriding type.

### 3.5. The attestation chain

Generic rule: `docs/review/workspace.md` section 2 (overrides need parity).

- **The in-tree chain.** Each parity and cross-backend registration's `backend_ref` is its attested same-ring link:
  - poulpy-cpu-portable: the oracle of its family and ring (`FFT64Oracle`, `NTT4x30Oracle`, `FFT64CIOracle`, `NTT4x30CIOracle`);
  - poulpy-cpu-avx and poulpy-cpu-arm: the portable type of their family;
  - poulpy-cpu-avx512: `FFT64Avx` and `NTT4x30Avx` (and CI forms), `NTT4x30Avx512` for `NTT3x42Ifma`;
  - a twin: its serial base, another attested backend only where needed;
  - BLAS parity and the AVX-512 one-pass and `idft_normalize` parity: the family oracle (NTT4x30 for NTT3x42 types);
  - word-compat: the portable sibling.
- **Encryption parity compares draws.** Encryption and key-generation parity runs under `with_backend_samples` against a backend drawing the same values from a seed (a twin's base, both on one `impl_sampling_host!` word family) or a `ControlledSampling*` type (`ControlledSamplingFFT64Portable` or its CI form for the SIMD crates, `ControlledSamplingFFT64Oracle` or its CI form for poulpy-cpu-portable, each serving both families), never a plain oracle type (`docs/review/workspace.md` section 10).

## 4. Overrides

Generic rules: `docs/review/workspace.md` sections 2 (the reference is the implementation, every operation through the OEP) and 3.

- **Specialize at the lowest level.** A CPU backend specializes at the lowest level reaching the operation: (a) its impl of the kernel trait the portable `*Default` body calls, forwarding the rest to `<op>_portable` or the trait default; (b) a split binding macro plus hand-written methods; (c) a hand-written family only for a transform-domain or prepared representation unlike portable's.
- **Primitives through the backend.** A vector-level portable kernel calls slice primitives through its backend's kernel traits (`BE::znx_add`), never the `*_portable` function of a primitive that has one.
- **Defaults are thin adapters.** An `<op>_default` reads the degree from `res`, asserts entry preconditions once, carves typed scratch and calls one `<op>_portable` kernel (FFT64: `module.get_fft_plan(n)`, NTT4x30: `module`) under method-level `where Self:` kernel-trait bounds, with no coefficient or limb loop of its own, and the kernels of `kernels/` and packed drivers of `ntt4x30/` take views, the module or a plan and a `tmp` slice, never a `ScratchArena`.
- **Kernel signatures mirror the operation.** A HAL-operation kernel takes the module, plan or table first, then exactly the HAL method's arguments in HAL order without `scratch`, then `tmp` last (a sampler: `source` last instead of the seed), entry kernels taking backend views with `BE::BufRef<'a>: HostDataRef` and `BE::BufMut<'a>: HostDataMut` bounds, never host-owned layouts, while inner helpers may be generic over `ZnxView`/`ZnxViewMut` or take `Limbs`/`LimbsMut`.
- **Fused overrides of derived bodies.** Besides HAL methods without a default body, `hal_defaults` and the binding macros bind only the fused `poulpy_hal::oep::*_derived` overrides that `docs/review/workspace.md` section 2 (every operation through the OEP) admits, each binding its `_tmp_bytes` too (unless under a family-wide query such as `vec_znx_lsh_tmp_bytes`), documented "CPU override of [`poulpy_hal::oep::<op>_derived`]: <what it fuses>, bit-exact with the default." and pinned by its `poulpy_hal::test_suite::derived` test on both portable backends.
- **Hand-written methods forward.** A hand-written family's method without a SIMD kernel forwards to the portable kernel or keeps the OEP default, and a core OEP override derives its output and digit limb counts with the reference's helpers (`poulpy_core::oep::gglwe_product_digit_output_size`, `gglwe_product_limbs`, gadget operands through `gadget_dft_apply`), never a local formula, and names that reference in its doc.
- **Limb-range tails as portable.** A hand-written element-wise transform-domain kernel reproduces the limb-range branches of `poulpy-cpu-portable/src/ntt4x30/vec_znx_dft.rs` (limbs both operands cover combine, limbs one operand covers are copied or negated as the reference defines, limbs past every operand are zeroed), and a kernel consuming its source in place (`vec_znx_idft_normalize`) rewrites only the named column, a test checking every other column bit identical.
- **Accumulating forms fuse.** An `_add` kernel accumulates into `res` in the product's pass with its overwriting form's scratch, leaving untouched the limbs past the computed range that form zeroes.
- **Core-level overrides.** A core-operation override asserts, before any write, `check_degree` and equal operand degrees, then the reference's public checks where it runs them (`assert_key_covers`, `assert_no_row_offset`, `assert_linear_transformation_into`, `assert_linear_transformation_sum`, key-source lookups at the input width), then `scratch.available() >= <its own query>`, and normalizes a flag-clear input into a scratch GLWE before its DFT kernels. Generic rules: `docs/review/workspace.md` sections 4 and 8.
- **Kernel API changes are breaking.** Renaming, removing or re-signaturing a `pub` item of `poulpy_cpu_portable::kernels`, a kernel trait or a binding or registration macro is `**Breaking:**` (`docs/review/workspace.md` section 17), a new kernel trait method has a portable default body where possible, and a new trait or required method is implemented in the same PR by `ZnxPortable`, both portable backends, the delegating fixtures, the poulpy-cpu-rayon forwarding macros and every SIMD crate.

## 5. Kernels

### 5.1. Validation

Generic rules: `docs/review/workspace.md` section 4 (checks live once, check before the first effect) and `docs/review/hal.md` section 9 (what every backend kernel must guarantee).

- **Entry checks before any effect.** A kernel asserts every HAL precondition before its first write, draw or table lookup, parameters and shapes first, then columns and the farthest limb (section 5.2), and a multi-term kernel validates every term before writing `res`.
- **`check_degree` where the module is.** Every computing kernel whose `domain` involves the module degree runs `check_degree::<BE>(module.n(), n)` before any table lookup, with or without a table, in the kernel when it receives the module, else in its binding body (`*_default`, `ntt4x30/hal_impl.rs`, the sampler macro), so no such default takes an unused `_module`, and a plan-taking kernel asserts `plan.fft().m() << 1 == res.n()`.
- **Columns, also on empty operands.** Every column argument is asserted `col < cols()` at entry, zero-limb operands included (a per-limb accessor is no column check), with "operand column out of range" ("convolution: result column out of range" for a convolution result).
- **Shared validators and messages.** A kernel validates through its family's helper, message verbatim, and its operation is registered in `vec_znx_dft_operand_validation` or the matching rejection suite: `poulpy_cpu_portable::kernels::fft64::vec_znx_dft::check_operand` in DFT kernels, `assert_extractable_portable` first in row extractions, `embedding_gap_portable` for embedded coefficient operands, `right_read_fft64` or `right_read_ntt` for convolution right operands, "<op>: step must be >= 1".
- **Density by operation kind.** Besides the window-refusing ops of `docs/review/hal.md` section 7, kernels addressing the dense buffer (`raw`, `raw_mut`, `as_ptr`, offsets from `n * cols`), `switch_ring` and the by-constant convolution call `assert_dense` at entry, and coefficient-wise kernels (add, sub, negate, copy, normalize, gadget decompose, noise) address limbs through `at`/`at_mut` or `scalar_offset`, accept windows and never assert density.
- **Slice lengths in release.** A per-limb slice kernel using raw pointers or vector loads asserts every slice length in release before its first load, `unsafe fn` kernels included, `debug_assert!` serving only bounds-checked code or an `unsafe fn ..._unchecked` behind a checked entry.
- **Parallel paths check before splitting.** A parallel path slicing limbs or coefficients itself runs the serial kernel's checks (`check_packed_operand` included) and probes the destination's last limb before creating a task, zero-limb vectors included, unless each task runs the same operand-only check before writing or the path falls back to the serial kernel below its threshold.
- **Secret-carrying kernels.** On the CPU backends the static-message rule of `docs/review/workspace.md` section 4 also covers `svp_ppol_copy`, the samplers, and the normalizations and `vec_znx_idft_normalize` of key generation, encryption and decryption, debug-only scans included.
- **Bounds stay caller obligations.** A SIMD kernel assumes a narrower input range than portable only where the HAL `domain` or `requires` clause or its in-crate caller guarantees it, names the bound in its name or doc, checks it at most under `debug_assertions`, and never backs a full-range contract.

### 5.2. Raw pointers and unsafe

Generic rules: `docs/review/workspace.md` sections 4 (hot paths carry no checks) and 7 (raw pointers from one base, unsafe documents its preconditions, Send and Sync).

- **Farthest limb, then one base.** A raw-pointer kernel bounds its farthest limb once in release (`if size > 0 { let _ = v.at_ptr(col, size - 1); }`) and derives every address, re and im halves and read and write cursors included, from one base (`base_ptr`/`base_mut_ptr`, `raw_mut().as_mut_ptr()`, `Limbs::new`/`LimbsMut::new`) plus `shape().scalar_offset(col, limb)` (`n()` the visible width, `n_full()` the limb stride), its `// SAFETY:` line citing those checks.
- **Safe wrappers argue the ISA.** A safe kernel-trait method calling a `#[target_feature]` kernel states in `// SAFETY:` the ISA source (x86: compile-time target features plus the constructor's runtime check; aarch64: the NEON baseline), the extent addressed and each task's disjoint range, and a raw-pointer helper is an `unsafe fn` naming the lengths it addresses and the overlaps it allows.
- **Disjoint writes through `SendPtr`.** A parallel kernel shares each output through one `poulpy_cpu_portable::kernels::SendPtr` taken from its base pointer after the entry checks (or a safe split such as `par_chunks_mut`), tasks getting disjoint regions and workers disjoint slices of one typed carve, no task a wider `&mut` view, no local `Send`/`Sync` wrapper, and each writing `// SAFETY:` line stating the disjointness.
- **Calls complete before returning.** A CPU backend, twins included, keeps the no-op `HalModuleImpl::synchronize`: all work joins before the call returns, detached work (`rayon::spawn`, `spawn_broadcast`) touches only the executor's atomics, no pointer into scratch or an operand survives the call, and handle caches hold only backend-owned data (deferred execution: `docs/review/hal.md` section 6).
- **Aliasing handled or refused.** A kernel computes correctly when `res` aliases or overlaps an input, or rejects the call on a defined path.

### 5.3. Arithmetic and rounding

- **Integer arithmetic wraps.** Word arithmetic the contract defines modulo the word (sums, accumulation, big-word products, noise added to the destination) uses `wrapping_*` or a wrapping trait (`MixedWord`, `NoiseWord`, `I128BigOps`) in lanes and tails alike, plain operators only for intermediates bounded by documented inputs.
- **Tails go to portable.** A SIMD kernel hands its remainder, and every size below its SIMD leaf, to the same operation's `*_portable` kernel on the tail sub-slices (`fft_portable_fused` below the FFT leaf), keeps a private scalar tail only where the layout withholds the remainder from it (split reim halves), repeating the portable formula exactly, and is unit-tested at lengths off the vector width.
- **Rounding as the contract states.** Kernels round as their contract defines (`rnd`, ties to even, in normalization, gadget decomposition and `idft_normalize`; half away from zero in `reim_to_znx` and the power-of-two division), a SIMD override matching portable at every rounding boundary, integer and NTT kernels bit-exact with portable, f64 kernels differing only in the last bits of DFT-domain values where they add an FMA, never in an integer result after the inverse transform, their unit tests alone using a stated tolerance.
- **Exactness bounds by construction.** A kernel family's fixed bound (term counts, products per reduction step, NTT bit widths, chunk sizes) is a named constant or table field whose doc derives it from operand bounds and accumulator width, enforced structurally or asserted when the table or schedule is built, never checked in the data.
- **Packed NTT4x30 invariants.** Packed residues stay canonical in `[0, q)`, one plane of `n` per prime per limb, prepared operands holding residues times `2^32` (the matrix and both convolution operands centered, in their kernels' read order), a new packed kernel keeps outputs canonical (`add_mod`, `sub_mod`, `mont_mul`, `stage_flush`), accumulates in `DotState` (at most `DOT_CHUNK` unit products per Montgomery step, a pairwise row weighing 4), allocates nothing, lives in `poulpy_cpu_portable::ntt4x30` and reaches poulpy-cpu-rayon only through `#[doc(hidden)] pub mod drivers`, and a change to the four-prime CRT kernels of `poulpy_cpu_portable::kernels::ntt4x30` keeps the AVX2 and AVX-512 NTT4x30 backends built on them in parity.
- **IFMA residues and packing.** `ntt3x42_ifma_dft_execute` returns fully reduced residues, `ntt3x42_ifma_dft_execute_lazy` output (in `[0, 4q)`) feeds only a re-reducing step (`ntt3x42_ifma_c_from_b`, `pack_limb_3x42_lazy`, `pack_limb_packed`) named in a comment at the call, and NTT3x42Ifma's packed bytes (`DftWord = Q126Scalar` an identity tag, `docs/review/hal.md` section 7; three 42-bit residues per two `u64`, `SvpPPol` six `u64` per coefficient) are sized by `checked_mul` overrides of every `Backend::bytes_of_*` and touched only through the pack and unpack helpers, never `at()` or a `Q126Scalar` slice, a layout change updating these and `test_packed_layout_zero_and_display` together.
- **Constants recomputed by tests.** Prime sets, `PrimeSet` impls and CRT constants live in the backend crate beside their word, never in poulpy-hal, and every hardcoded arithmetic constant (primes, roots of unity, CRT constants, Montgomery inverses and powers, cumulative distribution tables, accumulator bounds) has a unit test recomputing it (`P::validate()` plus primality, `LOG_Q`, the order `2^(MAX_LOG_N + 1)` of `OMEGA`, `q * qinv == 1`, extreme CRT values, exact table rebuilds, the accumulator inequalities).

### 5.4. Scratch and allocation

Generic rule: `docs/review/workspace.md` section 5.

- **No per-call allocation.** Kernel, driver and override bodies take temporaries from their query's scratch, fixed-size stack arrays or, in a scratch-free HAL entry, `poulpy_cpu_portable::kernels::with_thread_buffer` (written before read), an op needing a temporary never reporting 0, pass operand lists to drivers generic over the tagging backend, and leave allocation to builders of plans returned to the caller (automorphism plans).
- **One sizing function per temporary.** A kernel takes `tmp: &mut [T]` last and exports one `<op>_tmp_bytes_portable` or `*_tmp_words` function that its binding or hand-written method uses for the query (at `module.n()`) and the carve (at the degree of `res`, through `poulpy_cpu_portable::hal_defaults::take_host_typed::<Self, T>(scratch.borrow(), len)`, `T: bytemuck::Pod`), the kernel asserting that `tmp` covers its computed offsets; a body taking nothing reports 0, and `_add` and sibling queries forward to the base query.
- **Per-worker scratch from `ScratchWorkers`.** Every backend type implements `poulpy_hal::execution::ScratchWorkers` (serial: the empty impl), and a parallel kernel's query is `fixed + workers(cap) * per_worker` and its body runs `workers_within(cap, per_worker, scratch.available())` workers through `for_each_chunked` for one cap (`PREPARE`, `APPLY`, `VMP`, `IDFT`, min'd with the task count where known), a test pinning the formula and equal results for every budget from one worker's share to the query.

### 5.5. Module, tables and degrees

Generic rules: `docs/review/workspace.md` section 6 and `docs/review/hal.md` section 6.

- **Module construction.** `HalModuleImpl::new` is `hal_impl_module!(FFT64ModuleDefault)` or `hal_impl_module!(NTT4x30ModuleDefault)` with a handle factory (`create_*_handle`, `assert_*_runtime_support`), or follows its steps (IFMA's `module_new`): assert `n >= MIN_DEGREE` and the ISA's runtime support, build the tables of every power-of-two degree from `MIN_DEGREE` to `n`, return through `Module::from_nonnull`.
- **Tables in the handle.** Native transform tables and product metadata are built at construction in the handle for every served degree and read at the operand degree (`get_ntt_table_for(n)`, `get_intt_table_for(n)`, `get_fft_plan(n)`, `packed_table(module, n)`, `module.get_bbc_meta()`), `ModulePlanCache` (re-exported as `ModuleTableCache`) holds no native table, and a twin reuses its base's handle.
- **`MIN_DEGREE` is the floor.** On top of `docs/review/hal.md` section 6 (the degree floor), a raised `Backend::MIN_DEGREE` names in a comment the step of its tail-free kernels (`FFT64Avx512`: 16), those kernels assert that multiple, and no kernel keeps a private floor.
- **Ring-specific bodies per ring.** Ring-dependent kernels have one body per ring, under one name, in the `standard` and `conjugate_invariant` submodules of `kernels::{znx, fft64, ntt4x30}`, backends implement the ring-specific traits (`ZnxAutomorphism`, `ZnxAutomorphismRotate`, `Fft64RingArith`, `NttDFTExecute`) per concrete ring in `standard.rs` and `conjugate_invariant.rs` and ring-generic ones once over `R: Ring`, twins mirroring the split in `standard` and `conjugate_invariant` submodules, and defaults and macros never branch on the ring.
- **Ring macros and CI plans.** An FFT64-family backend's `Fft64RingArith` comes only from `poulpy_cpu_portable::fft64_ring_arith_standard!()` and `fft64_ring_arith_ci!()`, a new ring-dependent FFT64 operation being a new `Fft64RingArith` method in both, a CI NTT backend overrides `ntt_automorphism_plan` with the CI plan in its forward and inverse `NttDFTExecute` impls and wraps its transform in its basis change, and a SIMD negacyclic automorphism is wired on the standard ring only, the CI impl keeping `conjugate_invariant::znx_automorphism_portable` or a CI kernel tested against it.
- **The NTT degree bound.** Generic rule: `docs/review/workspace.md` section 6 (ring degree cap). The NTT prime sets keep `MAX_LOG_N = 18`, `max_ntt_degree_portable` halving the standard bound on the CI ring.

### 5.7. Storage, transfers and layout markers

Generic rules: `docs/review/workspace.md` section 7 and `docs/review/hal.md` section 7.

- **Host storage.** A host CPU backend sets `OwnedBuf = AlignedBuf`, `BufRef<'a> = &'a [u8]`, `BufMut<'a> = &'a mut [u8]` and `Location = Host` (or forwards them with `impl_backend_from!`), implements `alloc_zeroed_bytes` as `alloc_aligned::<u8>(len)` and, beside its `Backend` impl, its `ScratchWorkers` impl (section 5.4) and, with a model, the `MaxBase2k` impl of `docs/review/hal.md` section 6 (`max_base2k_ntt::<Self>` with its prime set's `LOG_Q_PRODUCT`, or `max_base2k_fft64::<Self>`).
- **Length-tolerant transfer hooks.** `from_host_bytes`, `copy_from_host` and `copy_host_to_view` accept a host slice at most the buffer length and zero the rest (`from_host_bytes` and `from_bytes` may return a longer, zero-tailed buffer), `copy_to_host` and `copy_view_to_host` copy the first `dst.len()` bytes, longer inputs panic, every hook reading storage observes all submitted work, and every type with its own storage impl (not an `impl_backend_from!` forward) registers `test_suite::transfer::test_transfer_padded_lengths`.
- **`DFT_LIMBS_CONTIGUOUS` only when true.** `Backend::DFT_LIMBS_CONTIGUOUS = true` requires limb `j` of column `i` at block `j * cols + i`, each `bytes_of_vec_znx_dft(n, 1, 1)` bytes, `bytes_of_vec_znx_dft(n, cols, size) == size * bytes_of_vec_znx_dft(n, cols, 1)` and every limb range a valid DFT vector; a `false` backend overrides `GGLWEProductDigitsStridedImpl` and `GLWEExternalProductImpl::glwe_external_product_dft` with their queries (`docs/review/core.md` section 1, DFT limb layout).
- **Layout markers for identical bytes.** On top of `docs/review/hal.md` section 7 (layout-compatibility markers), a `*LayoutCompatible` marker is declared in `layout_compat.rs` under a `# Safety` doc only between a type and its same-ring portable sibling, only for a container family whose bytes are identical for every shape (never the interleaved AVX2 NTT4x30 DFT or a backend-local `VmpPMat` or convolution layout), in both directions and for every serial, Rayon and CI form; a layout change adds or removes the marker and updates the pinned byte-size tests in the same PR, a layout deviating in any respect gets a new word type or no marker, and the change declaring a marker registers in a `cross_backend_test_suite!` `test_word_compat_dft_cross_idft` for every `VecZnxDft` marker (both directions run inside it) and the matching `test_word_compat_dft_bytes`, `test_word_compat_svp_prepare_bytes` and `test_word_compat_vmp_prepare_bytes` for markers over exact-arithmetic words.

### 5.8. Sampling

Generic rules: `docs/review/workspace.md` sections 2 (sampling happens in place) and 10.

- **One host sampler.** A production CPU backend implements `poulpy_core::oep::SamplingImpl` only through `poulpy_cpu_portable::impl_sampling_host!(BE, fft64 | ntt4x30)`, each method drawing from one local `Source::new(seed)` into the backend buffer, and a backend implementing it itself (the oracle, a controlled-sampling fixture) runs `test_sampling_contract`.
- **Samplers change together.** A new `SamplingImpl` method enters in the same change every sampler `docs/review/core.md` section 11 lists (a new sampled quantity), and a new sampleable `poulpy_core::Distribution` variant gets a `ScalarZnxFill` method and an arm in `scalar_znx_fill_distribution`, where non-sampleable variants keep panicking.
- **Samplers validate before drawing.** A sampler checks `noise.validate()`, radix, precision and column before any draw or write with the shared messages ("noise radix must be in 1..=63", "noise precision exceeds destination allocation", "noise column exceeds destination allocation", "noise degree outside module"), writes only the selected column's limbs below `ceil(k / base2k)` (a sample fitting one digit only the last), and draws depending only on seed, degree, law, radix and precision.
- **Exact laws, value-independent time.** A sampler draws the exact laws of `docs/review/core.md` section 11 (SamplingImpl contract) with exact integer arithmetic (its cumulative table built and certified at 128 bits, full-width samples decomposed across balanced limbs), table scans visiting every threshold, uniform bits consumed in fixed-size chunks and carries in fixed word arithmetic, tested by reconstructing complete integers beyond 128 bits, only its rejection path taking sample-dependent time and an ISA-dispatched variant consuming the scalar path's entropy in the same order.

### 5.9. CKKS encoding

Generic rule: `docs/review/ckks.md` section 10 (byte-identical encoding).

- **One arithmetic definition.** A backend's CKKS encoding transform reproduces `fft_portable_fused` and `ifft_portable_fused` whatever its layout or scheduling: the same radix-2 negacyclic butterflies on the same pairs (those by `i * w` and the inverse ones included, down to which sum is computed negated), one rounded product and one multiply-add per component (real `fma(br, wr, -(bi * wi))`, imaginary `fma(bi, wr, br * wi)`) and no other contraction, the correctly rounded `CKKSFloat::ckks_root_of_unity` twiddles of `EncodingFFTTable`, `ckks_quantize` and `ckks_dequantize`, and the default floating-point environment (round to nearest even, subnormals kept, no FTZ or DAZ).
- **Ring transforms stay unfused.** `fft_portable` and `ifft_portable` keep plain rounded products, only ring tables (`ReimFFTTable::new`) use `platform_root`, and encoding tables are built with `new_with_roots` from correctly rounded roots.
- **Selected through `CKKSEncodingTransform`.** A CPU backend customizes encoding only by implementing `ckks_encoding::CKKSEncodingTransform<F>` for the `impl_ckks_encoding!` encoder, generically over `F: CKKSEncodingScalar` with `EncodingFFTTable<F>` (portable and its twins) or, when accelerated, per precision through its `select_<isa>_encoding_transform!` macro for every type, CI forms and twins included (`f64` with `FFT64<Isa>EncodingTable = EncodingFFTTable<f64, ReimFFT<Isa>, ReimIFFT<Isa>>`, `Quad` with the portable `EncodingFFTTable<Quad>`), and a new `CKKSEncodingScalar` precision adds its line to that macro in every SIMD crate.
- **SIMD encoding is checked.** A SIMD crate keeps beside its encoding table `encoding_transform_matches_portable` (`test_negacyclic_fft_bit_exact` against `EncodingFFTTable<f64>` for every `log_m` in `0..=15`) and `raw_transform_matches_contract` (`test_negacyclic_fft`), and every backend registers the `determinism` tests (`docs/review/workspace.md` section 15).

## 6. The DFT slot law and block layouts

- **Every transform is bit-reversed.** Forward slot `i` of every CPU transform, new layouts included, evaluates at `omega^(2 * bitrev(i) + 1)` (CI: the first `n` slots of the standard degree-`2n` layout, FFT64 CI slot `s` at exponent `4 * bitrev(s) + 1`), a kernel mixing a degree-`n` operand into a degree-`N` sweep reads stored slot `i >> log2(N/n)`, and slot permutations derive from `build_fft64_automorphism_plan_portable` and `build_ntt4x30_automorphism_plan_portable` (a CI plan: the first half of the standard degree-`2n` plan, of `p` for FFT64, of the sign of `p` that is 1 mod 4 for NTT) or are tested against them slot by slot.
- **Only the right operand embeds.** Only the prepared right convolution operand (`CnvPVecR`) may be below the call degree, at least `BE::MIN_DEGREE` (`embed_log_gap_portable`), a prepare asserts its input has the prepared operand's degree and columns, and `cnv_prepare_self` asserts left and right agree in degree, columns and size.
- **Right reads through `RightRead`.** Convolution kernels build their right read with `right_read_fft64::<BE::Ring>` or `right_read_ntt::<BE::Ring>`, gather only when `!read.is_direct()`, and gather a row with one load and one lane permute from `read.lane_table::<W>()` at their layout's block width `W` (`read.block::<W>`, `read.conj()`), never per-lane scalar gathers (`docs/review/hal.md` section 9, embedded operands cost no more).
- **Respect the block layout.** A kernel takes its block structure from its own prepared layout: CI FFT64 reim4 rows hold two independent real quads (slots `4 blk + l` and `m + 4 blk + l`, gathered per lane), and NTT families store `CnvPVecR` rows in reversed limb order (`size - 1 - limb`).
- **Coefficient-domain embedding.** Only operations whose HAL contract has an `embed` line embed a coefficient operand of another degree, their kernels routing a degree differing from `res.n()` to the matching `*_mixed_portable` kernel, which reads with the `embedding_gap_portable` stride without building the embedding and writes every `res` limb in out-of-place forms.

## 7. SIMD crates

- **Refuse misconfigured builds.** An ISA crate root raises a `compile_error!` worded ``feature `enable-x` requires ...`` for its ISA feature on another `target_arch` or without an assumed `target_feature` (`avx2` and `fma` for `enable-avx`, `avx512f` for `enable-avx512f`, `avx512ifma` and `avx512vl` for `enable-ifma`, the message giving the `RUSTFLAGS="-C target-feature=+..."` fix), and for `enable-ckks` or `enable-bin-fhe` without it.
- **An empty shell off-target.** Without its ISA feature an ISA crate compiles only `capabilities` and its shell, with no `cfg(not(target_arch = ..))` fallback or in-kernel `cfg(target_arch)` gate, a new ISA or scheme feature brings its implication and guard, and a new poulpy-cpu-avx512 target guard carries `not(docsrs)`.
- **Runtime detection in the factory.** An x86 backend checks with `is_x86_feature_detected!` every extension its kernels enable, explicitly named implied ones included (`FFT64Avx512`: avx512f, avx2, fma), once, in its handle factory hook (`FFT64HandleFactory::assert_fft64_runtime_support`, `NttHandleFactory::assert_ntt_runtime_support`, IFMA's `module_new`) before any table, panicking with a static message, kernels never re-detect (tests may, to skip), NEON keeps the no-op hook, and the runtime check, the `compile_error!` guards, the `capabilities.rs` target-feature string and the AVX-512 job's target flags and detection probe list the same extensions, implied ones aside, a kernel adopting another extension updating all four in the same PR.
- **`target_feature` on x86 only.** Every x86 function issuing SIMD intrinsics carries `#[target_feature(enable = ...)]` with each extension it needs, `#[inline(always)]` helpers called only from such functions excepted, the safe kernel-trait impl calling the kernel inside `unsafe { }` (section 5.2), and NEON kernels carry none, a NEON slice kernel being an ordinary `pub(crate) fn`.
- **The AVX-512F baseline.** poulpy-cpu-avx512 uses only AVX-512F (with AVX2 and FMA) plus AVX-512-IFMA and VL in IFMA kernels, float sign and bit operations going through integer ops on cast registers (`_mm512_xor_si512` over `_mm512_castpd_si512`), never DQ, BW, CD or VBMI intrinsics (`_mm512_xor_pd`, `_mm512_and_pd`, `_mm512_or_pd`).
- **Fill zmm registers.** AVX-512 and IFMA kernels and lane types fill 512-bit registers (`ZnxNormalize`: `SimdLanes<16>`, `SimdI128Lanes<8, false>`, `SimdI128Lanes<16, false>`), widths argued for a native 512-bit datapath, Zen 4 measurements gating only regressions, and a cache cliff fixed in the walk.
- **Unaligned loads and stores.** SIMD kernels load and store with the unaligned forms (`_mm512_loadu_*`, `vld1q_*`, `read_unaligned`) and assume no alignment of operands, windows, limb ranges, carves, tables or stack arrays.
- **Non-temporal stores.** A streamed store (`_mm512_stream_si512`, `_mm256_stream_si256`) writes only a 64-byte-aligned (`DEFAULTALIGN` owned or `SCRATCH_ALIGN` carved) DFT-domain or prepared destination at vector-width block offsets, alignment checked at run time (`dst.addr().is_multiple_of(64)` with a `storeu` fallback) or argued, only for outputs not re-read soon (`cached_overwrite_stores`), each streaming task issuing `_mm_sfence()` before the join and the serial path fencing before returning or reloading.
- **FFT16 assembly, both object formats.** A change to the AVX2 FFT16 `.s` files or symbols updates both `global_asm!` blocks of `poulpy-cpu-avx/src/fft64/reim/mod.rs`, Mach-O (`target_vendor = "apple"`: leading underscore, `.private_extern`, no ELF-only directive) and ELF (`.hidden`, `.type`, `.size`, `.note.GNU-stack`), and the `unsafe extern "sysv64"` declarations.
- **Shared kernels written once.** Coefficient-domain AVX-512 kernels live once in `znx_avx512` and i128 helpers in `vec_znx_big_avx512`, and scalar mirrors of SIMD kernels (`ntt3x42_ifma::reference`) are crate-private and `#[cfg(test)]`-only.
- **Measured routing away from SIMD.** Routing to the portable kernel instead of an existing SIMD one, or to scalar loops instead of vector gathers, states its measurement (sizes, speedup, machine) beside the choice, and a SIMD kernel left unreachable is removed. Generic rule: `docs/review/workspace.md` section 17 (performance claims cite a bench).
- **Kernel docs name counterparts.** A SIMD kernel's doc names the portable kernel or reference body it reproduces, which its unit test compares with, and a port from another library keeps the DISCLAIMER header (source, Apache-2.0 license, one-to-one or reworked, the matched C function for a one-to-one port).

## 8. Rayon twins

- **Twins are retagged markers.** A twin is an `impl_backend_from!(Twin, Base, Executor)` marker (`Executor`: `RayonTaskExecutor`, or for a hand-built twin an executor built on it, such as `NTT3x42IfmaRayonExecutor`) sharing its base's handle, `OwnedBuf`, words, ring, `MIN_DEGREE` and DFT layout, and reaches the base only by retagging in place (`module.reinterpret()`, the `base_*_ref` and `base_*_mut` helpers, `scratch.borrow().into_backend::<Base>()`), never by building a module, copying a buffer or allocating scratch, a delegating backend built with `impl_backend_from!` forwarding the same way.
- **Twins from the shared macros.** A twin is built per ring with `impl_fft64_rayon_backend!(Twin, Base)` or `impl_ntt4x30_rayon_backend!(Twin, Base)` in `mod standard` (with `hal_impl_vec_znx_monomial!`, `hal_impl_vec_znx_ci!`, `ZnxAutomorphismRotate` forwarded to the base and, for FFT64, `fft64_ring_arith_standard!`) and for `Twin<ConjugateInvariant>` in `mod conjugate_invariant` (`fft64_ring_arith_ci!`), `RayonTuning` and `ScratchWorkers` once over `R: Ring`, all behind `enable-rayon` and any further ISA feature, and is hand-built only where no shared driver serves its base's layout (NTT3x42IfmaRayon).
- **The packed NTT4x30 base.** `impl_ntt4x30_rayon_backend!` takes a `PackedWord` base implementing `PackedNtt4x30Base`, through `impl_packed_ntt4x30_base!(Base, Ring, drivers)` (private `drivers` functions mirroring each trait method's name and arguments, generics ring first: `<R, E>`, `<R, BE, E>` for the convolutions) or by hand where it overrides a method the macro leaves at its default (`cnv_apply_dft_sum`), splitting drivers take `E: TaskExecutor` and never name `RayonTaskExecutor`, and a new required `PackedNtt4x30Base` method enters in the same PR the macro, the AVX2 and AVX-512 NTT4x30 `drivers`, `impl_packed_base!` of `poulpy-cpu-rayon/src/portable/ntt4x30.rs` and `poulpy-cpu-arm/src/ntt4x30/rayon.rs`.
- **Kernels generic over the executor.** A kernel shared by a serial type and its twin is generic over `E: TaskExecutor` (and over the backend tagging its operands where the twin's types differ; the serial OEP passing `SerialTaskExecutor`), splits only under `E::is_parallel()`, and every split runs the serial base path on a one-thread pool and in a nested region (`RayonTaskExecutor::should_serialize_inner()`), sizes its work with the shared helpers (`workers`, `workers_within`, `parallel_chunk_len` with chunks rounded to 64 coefficients, `parallel_limb_tasks`), never a local copy, and takes a new threshold as a `RayonTuning` constant (section 10).
- **Twins return their base's words.** A twin returns its base's exact words for every input, pool width and nesting depth, its splits only partitioning work that each task runs through the base's kernel and every unsplit operation forwarding to the base, and a hand-written twin family or kernel trait parallelizes or forwards (`<$base as Trait>::method`) every method its base specializes, default-bodied ones included, and every base query trait (`MaxBase2k`), rechecked whenever its base gains an override, a trait gains a defaulted method or a query trait is added.
- **Twin queries follow the bodies.** A twin's query is the base's query on the base module for a forwarded op, its pool-independent per-worker sizing (section 5.4) for a parallel body and the maximum over paths for a body choosing at run time, a hard-coded 0 only where the macro documents a scratch-free base.
- **Regions keep the nesting state.** A splitting `RayonTaskExecutor` region runs each task under `TaskGuard::enter(depth, share)` with `depth = TASK_DEPTH + 1` and a share of `task_budget()` (join: ceiling and floor halves; `for_each` and `for_each_chunked`: one share per task or worker), calls `idle::region_opened()` at depth 1 and joins every task, a calling-thread path leaving depth and budget untouched, `for_each_chunked` asserts `scratch.len() >= per_worker` with the HAL default's "worker scratch" prefix, and work whose tasks may open regions goes through `RayonTaskExecutor::{join, for_each, for_each_chunked}`, never a raw rayon iterator.
- **Normalization in twins.** A twin forwards `ZnxNormalize` to its base and normalizes through `poulpy_cpu_rayon::normalize::{vec_znx_normalize_par, vec_znx_normalize_assign_par, vec_znx_big_normalize_par}::<Base, Twin>`, which split coefficient ranges at multiples of 8 through the `*_range_raw_portable` kernels and run the base's serial kernel below two `NORMALIZE_MIN_TASK` tasks or in a nested region.

## 9. The oracle

- **Required methods only.** The oracle implements exactly the required OEP methods of each HAL family, inheriting every default body unless the default cannot run there, a comment above such an override saying why.
- **Bodies read as the definition.** An oracle body follows the contract's `definition` literally: plain loops through checked accessors (a `// res[j] = ...` comment where a combinator hides the formula), zero-extension through the `limbs` combinators, embeddings materialized first (`embed::with_vec_znx`), ring-dependent steps through `ring::` (CI in the standard ring of degree `2n`, standard-only families on `Oracle<F, Standard>` only), and heap temporaries with a `_tmp_bytes` of 0.
- **Serial, safe and plain.** The oracle keeps `SerialTaskExecutor`, the default `ScratchWorkers`, no SIMD, Rayon or fast path, no `unsafe` block or function beyond its module handle in `backend.rs` (its OEP `unsafe impl`s aside), and unoptimized arithmetic, performance work limited to building and caching its tables.
- **Independent tables and constants.** Every oracle table and constant is derived inside the oracle from its definition (FFT twiddles from the float type's own trigonometry, NTT roots, inverses and CRT constants from its own prime set, `ckks_roots` by fixed-point integer arithmetic, normalization and gadget decomposition on arbitrary-precision integers, Gaussian draws by its own rejection sampler), production values are checked against it (`production_roots_match_independent_derivation`), and no oracle body calls the code it attests.
- **The oracle's encoding.** The oracle encodes through the CKKS reference circuit (`poulpy_ckks::reference::encoding`, `CKKSSlotEmbedding`) over its own `EncodingFft`, whose butterflies round `b * w` with one multiply-add per component on the roots of `ckks_roots`, and an encoding-contract change updates `EncodingFft` and `ckks_roots` together with the portable kernels, `production_roots_match_independent_derivation` and the determinism fixtures passing without regenerating either side from the other (`docs/review/ckks.md` section 10).
- **Independent and controlled sampling.** The oracle's `SamplingImpl` uses its own algorithm (`impl_independent_sampling!`: uniform rejection over the bounded interval, an exact Bernoulli(exp(-x)) coin) on the law of `Noise::gaussian_parts`, its `ControlledSampling*` types copy the tested backend's draws (`scalar_samples`, `add_noise_samples`), and every noise body validates before writing with the messages of section 5.8.
- **Registrations through its macros.** Families shared by several oracle types register through `impl_oracle_core!` and `impl_oracle_core_standard!` in `core_impl.rs` and `impl_oracle_ckks!` and `impl_oracle_ckks_standard!` in `ckks.rs`, never per-type lines, a new family entering the macro whose types need it, with `impl_bin_fhe_reference_full!` on the two standard oracles and `impl_blas_reference_full!` on all four.

## 10. Fast-path gates and tuning constants

- **One predicate, body and query.** Generic rule: `docs/review/workspace.md` section 5 (override body and query together). A specialized override falls back on the other side of its predicate to the public `*_reference` body and `*_tmp_bytes_reference` query together, or asserts that it fits the reference budget and returns the reference query, and a specialized kernel inside a reference body adds its whole scratch to the reference query under the same predicate.
- **Decide first, refuse alike.** A specialized path decides applicability before its first write, otherwise reaching the reference with the destination untouched (`return false`, or an early `return module.<op>_reference(..)`), its predicate names every operand or key property it does not handle (radix mismatch, `stride() != 1`, `k_offset() != 0`, `dsize() < 2`, a key row offset, digits off a limb boundary it does not lay out, a destination below the module degree, degree, rank and shape caps) so those inputs reach the reference, a path consuming a key applies the reference's checks (`get_tensor_key(..)` errors, `assert_no_row_offset`), and each new reference refusal or key property enters every predicate of the crate in the same PR (`docs/review/workspace.md` section 4, overrides refuse like the reference).
- **Gate constants carry measurements.** Every performance constant or attribute (a `*_MIN_DEGREE`, `*_MIN_N` or `*_MIN_SIZE` gate, a tile, block, chunk, group or task size, a lane width, the Rayon `COEFF_MIN_*`, `NORMALIZE_MIN_TASK` and `LIMB_TASKS_MIN_N` thresholds, a `ScratchWorkers` cap, an `#[inline(never)]` boundary) is a named `const` whose doc gives its measurement (crossover or speedup, degrees and thread counts, machine), hardware reason or copied twin values (`RANK_ONE_TENSOR_MIN_DEGREE` in `poulpy-cpu-avx512/src/core_impl.rs`), an unmeasured `ScratchWorkers` family keeping its serial default.
- **Both sides of every gate.** Registered parity cases reach both sides of every specialization predicate, a degree or size gate through `const X: usize = if cfg!(test) { .. } else { .. };` (`2^8` for degree gates, documented) or a native suite at and around the production threshold (`ntt_n*`, `core_parity_*_fused`, `*_streaming`), and adding or deleting a specialization follows `docs/review/workspace.md` sections 2 and 17.

## 11. Features, examples and benches

Generic rules: `docs/review/workspace.md` sections 14 (feature names and gates, test-only features) and 16 (map configurations to lanes, wiring new jobs and features).

- **SIMD crate features.** A SIMD crate's features are `enable-<isa>` (`enable-avx`, `enable-avx512f`, `enable-ifma` implying it, `enable-neon`), `enable-rayon` (implying the base ISA, enabling `dep:poulpy-cpu-rayon`, gating every twin), `enable-ckks`, `enable-bin-fhe` and `enable-blas`, core a plain dependency with no feature, scheme wiring gated `#[cfg(all(feature = "enable-<isa>", feature = "enable-<scheme>"))]` and tests `#[cfg(all(test, feature = "enable-<isa>"))]`.
- **Features forward.** A backend's `enable-<scheme>` enables `dep:poulpy-<scheme>` plus the same feature on every workspace backend crate whose implementations or registration macros it reuses (`poulpy-cpu-portable/enable-<scheme>`), poulpy-cpu-avx512's `enable-avx512f`, `enable-rayon`, `enable-ckks` and `enable-bin-fhe` also enable the matching poulpy-cpu-avx feature (`enable-avx512f`: `poulpy-cpu-avx/enable-avx`), and a new feature copies its siblings' implications in every backend manifest, poulpy-cpu-rayon and the oracle included.
- **Wiring a layer.** Wiring a scheme layer adds in one diff `enable-<layer>` with its forwards, `#[cfg(feature = "enable-<layer>")] mod <layer>_impl;` with the registrations and paired suites, the `# Features` doc and README entries, and the lane feature set (`PORTABLE_FEATURES` for poulpy-cpu-portable, poulpy-cpu-rayon and poulpy-cpu-oracle; `AVX_FEATURES`, `AVX512_FEATURES`, `NEON_FEATURES`; the `.github/scripts/test-backend.sh` per-mode features for AVX lanes).
- **Test adapters stay test-only.** What `poulpy-cpu-portable/enable-test-suite` exposes compiles only under `#[cfg(any(all(test, feature = "enable-core"), feature = "enable-test-suite"))]` (`ckks_comparison`: `any(test, feature = "enable-test-suite")`), and probe backends used only by the crate's own tests are `#[cfg(test)]`.
- **No ISA gates in portable.** poulpy-cpu-portable chooses no algorithm or lane width by `cfg(target_feature = ..)`, per-ISA tuning coming from the SIMD backend's kernel-trait associated types or overridden methods, its only ISA-specific code being a runtime-detected `#[target_feature]` copy of the same body or a `cfg(target_arch)` choice between bodies with bit-identical results and entropy use, pinned by a test or by IEEE semantics, its `cfg` only skipping the dispatch where the feature is present (`not(target_feature = "fma")`).
- **Combinations no lane builds.** Code compiled only in a serial build, under `enable-avx512f` without `enable-ifma`, under one scheme feature alone or in a `#[cfg(not(feature = ..))]` arm is compile-checked by hand on that combination (`cargo clippy -p poulpy-cpu-avx512 --all-targets --features enable-avx512f`), the PR saying so, and a feature-only import carries the same `#[cfg]`.
- **Targets declare their features.** A bench, example or integration test needing a feature declares it in `required-features`, and an ISA crate example gates its body on `all(feature = "enable-<isa>", target_arch = ..)` (plus `target_feature = "avx512f"` on AVX-512) with a fallback `main` that prints why it skips or picks the portable type (`docs/review/workspace.md` section 1, runnable examples).
- **Bench binaries.** The `benches/` binaries of these crates follow `docs/review/bench.md` section 4 (backend bench binaries).

## 12. Docs and public surface

- **Crate docs state the contract.** A backend crate's root doc lists every Cargo feature with what it enables and implies, an ISA crate's also its public API under "Versioning and stability", and its docs and README state only what the code does (which outputs are bit-exact with portable or within a tolerance, the instructions relied on, aligned loads, non-temporal stores and assembly included, the module table, the CI coverage), a diff adding a feature, type or public export or changing such a property updating them in the same diff. Generic rule: `docs/review/workspace.md` section 13.
- **Portable plumbing is hidden.** A `pub` item of poulpy-cpu-portable used only by other CPU crates (a defaults trait, a driver, `SendPtr`, `with_thread_buffer`, `check_operand`, the `*_range_raw_portable` entries, `ntt4x30::drivers`, a registration module) is `#[doc(hidden)]` and documented as carrying no stability promise, while `hal_defaults::take_host_typed` and the `kernels` module are documented API. Generic rules: `docs/review/workspace.md` sections 2 (minimal visibility) and 14.
- **Rayon and SIMD surfaces.** poulpy-cpu-rayon documents the twin macros, `RayonTaskExecutor`, `RayonTuning`, `PackedNtt4x30Base`, `PackedWord`, the scheduling helpers, the idle-polling setters and `tuning`, its items exported only for expansion in other crates being `#[doc(hidden)]` (`rayon_forward_i128_big!`, `impl_packed_ntt4x30_base!`, `check_packed_operand`, the `SendPtr` re-export, `__private`); a SIMD crate exposes its backend markers and CI aliases, the encoding-table aliases, the FFT executors (`ReimFFT<Isa>`, `ReimIFFT<Isa>`), `capabilities` and, in poulpy-cpu-avx512, `ntt3x42_ifma_api`, its kernels, drivers, handles and helpers staying `pub(crate)` or private and plumbing another crate needs being `#[doc(hidden)]` (`NTT3x42IfmaRayonExecutor`).
- **Crate-wide `too_many_arguments`.** poulpy-cpu-portable and poulpy-cpu-oracle allow `clippy::too_many_arguments` crate-wide, so new items there carry no suppression of it (`docs/review/workspace.md` section 13, lint suppressions).

## 13. Tests and registration

Generic rules: `docs/review/workspace.md` section 15 and `docs/review/hal.md` section 11.

### 13.1. Where tests live

- **Backend crates instantiate.** A backend crate hand-writes tests only for its own kernels, layouts, constants, models and registration plumbing, plus thin `#[test]` wrappers of suite functions no macro covers, and a suites-only file (`poulpy-cpu-portable/src/tests/ckks_tests.rs`) keeps its "There should be no hand-written test here" true, the dispatch probes of `poulpy-cpu-portable/src/tests` (section 13.5) excepted.
- **Kernel tests beside the kernel.** A backend-specific kernel's test sits in a `#[cfg(test)] mod tests` beside it or in `src/tests.rs` and compares bit for bit, or within the stated FMA tolerance, with an independent definition (exact `dashu` arithmetic, a direct formula, the oracle, an independent second kernel) over shapes reaching every branch (tails, edge offsets, empty sizes, overwrite and accumulate), and twin-macro code is tested inside the macro body (`mod fft64_rayon_tests`, `mod ntt4x30_rayon_tests`) at one call per op at the gate degree.
- **Shared kernel checks.** A kernel trait that SIMD backends override has a bit-exact check in `poulpy_cpu_portable::test_suite` (a `pub fn test_*<BE: KernelTrait>()` or a `#[macro_export]` suite macro) against the `_portable` kernel or an exact integer oracle, over every lane width plus a scalar tail and the bound extremes (`+-2^62`, `i64::MIN`, `i64::MAX`, residues 0 and `q - 1`, rounding ties), called for every implementing type, twins, IFMA and the delegating fixture included (a ring-generic impl through its standard instantiation), a new overridden trait or method adding its check there.
- **Rejection tests pin the message.** A backend crate's own rejection test pins the kernel's exact message (`#[should_panic(expected = ..)]`, or `catch_unwind` with a downcast to the shared string) and, where the kernel rejects before mutating or drawing, checks the destination and source unchanged.
- **Library tests on x86 lanes.** Tests of poulpy-cpu-avx and poulpy-cpu-avx512 live in `src/`, and a test owning its binary (a counting `#[global_allocator]`) is a `[[test]]` with `required-features` in poulpy-cpu-portable, poulpy-cpu-rayon, poulpy-cpu-oracle or poulpy-cpu-arm, or the PR states how it runs.

### 13.2. Registration lists

- **New HAL tests everywhere.** The lists of `docs/review/hal.md` section 11 (register on every backend) are portable `src/tests.rs` (one list per family and transform), the SIMD `fft64/tests.rs`, `ntt4x30/tests.rs` and IFMA lists, and the oracle's `src/tests.rs` (a `cross_backend_test_suite!` of `FFT64Oracle` against `NTT4x30Oracle`) and, unless the op is monomial-only, `src/tests/conjugate_invariant.rs`, a twin's list gaining a test only when the twin parallelizes or overrides the op, and production-only and backend-free tests skipping the oracle.
- **The full HAL lists.** Each SIMD crate registers per family the full HAL lists, identical between AVX and NEON apart from `word_compat` (`cross_backend_test_suite!` modules `vec_znx`, `svp`, `vec_znx_big`, `vec_znx_dft` and `vmp`, `backend_test_suite!` modules `derived`, `sampling`, `window`, `lwe_matrix` and `vec_znx_dft_operand_validation`, `test_convolution_direct`, a `word_compat` module per declared marker, and for twins `vec_znx_dft_rayon` against the base, `window_rayon` and `vec_znx_dft_operand_validation_rayon`), a type omitting only what its families cannot implement (a CI form exactly the monomial-family tests: `rotate`, `mul_xp_minus_one`, their derived tests, the window rejection test calling `rotate`), and operand re-view variants (`scalar_znx_automorphism`, `scalar_znx_ci_embed`) registering once, on portable and the oracle.
- **Validation suites.** `test_vec_znx_dft_rejects_invalid_operands` and `test_vec_znx_dft_transforms_reject_invalid_operands` are registered with `n` at `MIN_DEGREE` and `size` above it (`size: 16, n: 8`; `size: 32, n: 16` on the FFT64Avx512 types) for every type, each twin included.
- **Every layer's suites run.** Each type registered for a layer runs that layer's suites in the same crate (core parity and encryption parity, the CKKS backend, parity and encryption-parity suites, the bin-fhe, mhe and blas suites, section 13.4 for a CI form), while `core_backend_test_suite!` runs only on the portable backends and the oracle.
- **Every sibling form.** A suite registered for one type is registered at matching params for every sibling form it applies to (the HAL lists, `test_convolution_direct` and, for NTT types, `ntt_n1024` to `ntt_n32768` for every serial standard type; the CI bundles of section 13.4 for every CI form; the core, CKKS and BLAS suites for every serial and twin, standard and CI, `f64` and `Quad` form), an omission stating its reason beside the registration (`docs/review/workspace.md` section 15, coverage narrows, never switches off).
- **Complete core parity lists.** Every `core_parity_test_suite!` registration lists every core contract the macro takes (each `poulpy_core::test_suite::parity::test_*_parity`, `test_preparation_contract`, `sampling::test_sampling_contract`), `core_encryption_parity_test_suite!` covering the same pairs, a new contract entering every registration of every crate, fewer only in a narrowing registration (`core_parity_rank1_only`) and the CI lists (no monomial families); a twin against its base sets `ParityShapes { unaligned_digits: false, ..Default::default() }`, large-degree fused suites `ParityShapes { ranks: vec![1], dsizes: None, unaligned_digits: true }`, and focused large-degree cases (`test_glwe_tensor_parity_for_layout`, `core_emulated_tensor`) complement the full small-degree registration, never replace it.
- **CKKS lists.** Each CKKS type registers, behind its features, `ckks_backend_test_suite!` at its family's parameters (`BASE19_PARAMS_F64` for FFT64, `BASE52_PARAMS_F64` for NTT, plus `BASE52_PARAMS_QUAD` where it runs `Quad`), `ckks_parity_test_suite!` modules `_f64`, `_quad` and `_rank2`, `ckks_encryption_parity_test_suite!` at ranks 1 and 2 and its CI form's `ckks_parity_ci_*` modules, a new parity helper joining them in every crate (`docs/review/ckks.md` section 15.1).
- **The CKKS comparison radix.** CKKS parity and encryption parity run at `CKKSTestParams { n: 64, hw: 48, base2k: <b>, ..<family params> }` (`rank: 2` for rank 2), `<b>` being 12 against the oracle, across families and for encryption parity, and at most the family radix (19 for FFT64, 52 for NTT) within a family.
- **Preset precision tests.** `bootstrapping_presets_meet_precision` (ignored) takes radix 18 for FFT64 and 52 for NTT, and `small_s2c_preset_meets_precision` is registered only on types whose radix takes the preset's 52 bits.
- **bin-fhe suites.** `poulpy_bin_fhe::bin_fhe_backend_test_suite!(mod bin_fhe_<family>[_rayon], backend = Type)` sits in the crate's `tests.rs` behind `enable-bin-fhe` and its ISA cfg, a check every type must run goes into the `register_backend!` parity suite (`docs/review/bin-fhe.md` section 11), and a hand-written override's test calls `poulpy_bin_fhe::test_suite::parity::<family>::test_<op>_parity` with the override as the tested backend and counters proving the override and its query ran and any extra reserved region intact.
- **blas suites.** A `blas_tests` module (`src/tests/blas_tests.rs`, or beside the types as `poulpy-cpu-rayon/src/portable/blas_tests.rs`) under `enable-blas` holds only `blas_parity_test_suite!` for every type against its family oracle (modules `blas_parity_[ci_]<type>_<variant>`, `<variant>` one of `f64`, `quad`, `rank2`, `base2k54`, `n32`), `blas_conjugate_invariant_test_suite!` per CI form (`blas_ci_<type>`) and, in poulpy-cpu-portable and poulpy-cpu-rayon, `blas_max_base2k_test_suite!` per family and ring, `blas_backend_test_suite!` running on the oracle only and a new heavy variant taking a suffix of section 13.7.

### 13.3. Degrees, shapes and pools

- **Floor and module degree.** HAL registrations follow `docs/review/hal.md` section 11 (`n: 16` on the FFT64Avx512 types), `(module, n, base2k)` suites run at `<BE as Backend>::MIN_DEGREE` and at `module.n()`, and an op whose kernel changes path above a degree or chunk length gets a registration crossing it.
- **Sub-degrees in portable.** Core and scheme parity registrations compute at the module degree (`n == size`, commented "computes at the module degree, no sweep"), the sub-degree core registrations (`test_size` above `params.size`) living in `poulpy-cpu-portable/src/tests.rs`, one per family, which every new core parity or encryption-parity helper joins.
- **Twins above their floors.** Every split and override of a twin is reached by a parity registration against its base (BLAS: the family oracle) whose degree crosses the split's floor (`LIMB_TASKS_MIN_N`, `NORMALIZE_MIN_TASK`, `COEFF_MIN_LEN`, more than one convolution block per worker), with a comment naming it, or by a dedicated large-ring case.
- **Parallel tests own their pool.** A test that must take a parallel branch installs its own pool (`rayon::ThreadPoolBuilder::new().num_threads(k).build().unwrap().install(..)`) wide enough to cross the parallel floors.

### 13.4. Conjugate-invariant suites

- **The CI bundle.** A CI form registers in `lib.rs` `poulpy_cpu_portable::conjugate_invariant_test_suite!` and `conjugate_invariant_core_test_suite!` (CI type, standard sibling, attested CI reference per section 3.5, the serial CI type for a twin) and, with CKKS, `poulpy_ckks::conjugate_invariant_ckks_test_suite!`, its `ckks_parity_ci_*` and `blas_parity_ci_*` lists and `blas_conjugate_invariant_test_suite!`, the oracle CI types using `core_parity_ci` instead of the core macro.

### 13.5. Probes and override tests

- **Counting probes for hooks.** An OEP hook that a provided composition must reach gets a `poulpy-cpu-portable/src/tests` probe whose counting override forwards to the `*_reference` functions with a distinct extra scratch, and a public-API test asserting that every operation over the hook enters it, its query includes the extra, the output matches the oracle and API-rejected calls never enter it (`docs/review/workspace.md` section 3, compositions use selected implementations).
- **Probe fixtures and pattern.** A probe lives on an `impl_fft64_delegating_backend!` fixture or, for a backend-agnosticism contract, an opaque backend (`OpaqueBackend<'env>` of `poulpy-cpu-portable/src/tests/bin_fhe_overrides.rs`), never a production backend, takes `scratch.borrow().take_region(EXTRA)` first, fills it with a pattern, passes the rest to the reference and asserts the pattern intact, reports the reference query plus `EXTRA`, and runs on exactly that budget poisoned with `0xA5`, asserting the call count and the query value and counting with `thread_local!` counters or, on worker threads, `Mutex`-guarded static atomics.
- **Scheme probe files.** `poulpy-cpu-portable/src/tests/ckks_overrides.rs` probes every new CKKS composition reaching another CKKS family or core (shared queries such as `ckks_all_ops_tmp_bytes` included, core-following queries through `CoreQueryOverrides`), and `tests/blas_overrides.rs` follows `docs/review/blas.md` section 11.
- **Core-level overrides tested.** A backend's core-level override has a CI-filtered test module (`relinearize_tests`, `prepared_tensor_tests`) comparing it with the `*_reference` method, each side on its own poisoned budget, at a small and at the gate's production degree, over mixed radixes and off-limb digit widths, with flag-clear inputs, unchanged inputs and prepared operands, garbage-filled outputs and a one-byte-short budget panicking without mutating the output where they apply, and a fused `GGLWEProductDigitsStridedImpl`, serial or twin, also calls `poulpy_core::test_suite::parity::test_gglwe_product_digits_strided` on its own module.
- **Fused finish kernels.** A fused inverse-transform and normalization kernel is tested against the portable composition on edge coefficients (0, `+-1`, `+-2^(base2k-1)`, `+-Q/2`, large values) and precisions (0, 1, `base2k`, `base2k + 1`, partial and beyond the full width), addends of several sizes including none, untouched source columns, a module at twice the operand degree and, when parallel, pool widths 1, 3, 16 and 48, a nested region and budgets below its query.

### 13.6. Oracle self-tests and fixtures

- **The oracle attests itself.** Each oracle transform, table, ring map and sampler has a unit test against its mathematical definition, never another backend (transforms against direct polynomial evaluation and `test_negacyclic_fft`, the prime set against its roots and modulus size, the CRT at the signed boundaries, CI products and automorphisms against the schoolbook product and the basis action, spectrum against coefficient embedding, the sampler against the discrete PMF, normalization at ties and carries), and the oracle cross-checks its FFT64 and NTT4x30 families (HAL, core, CKKS and BLAS parity both ways, at `base2k` 12) and runs the functional suites (`core_backend_test_suite!`, `ckks_backend_test_suite!`, `blas_backend_test_suite!`, the CI suites) and bin-fhe's parity and reference suites.
- **Two sets of key digests.** The `test_glwe_public_key_rank1_golden` digests of poulpy-cpu-portable (portable's sampler, also reproduced by its ControlledSampling oracle runs under `with_backend_samples`) and of the oracle (its own sampler) change together, by hand, only with an intended sampler or wire-format change, and the CKKS determinism fixtures also run on the oracle (`ckks_encoding_determinism_f32`).

### 13.7. CI selection and emulation

Generic rules: `docs/review/workspace.md` section 16 (filtered lanes select by name, emulated runs fit their budget, renames move the CI references).

- **Which lanes filter.** A backend test meant for the filtered runs carries a name their filters select (`core_parity_*`, `core_encryption_*`, modules under `tests::blas_tests`, a HAL entry's own function name; native AVX-512 only: `ckks_parity_*`, `bin_fhe_parity_*`), and no override's only AVX-512 coverage is an in-module kernel test (`*_vs_ref`), a `ckks_backend_test_suite!` or `bin_fhe_backend_test_suite!` registration (filter-matching tests such as `encoding_determinism` aside) or a noise test.
- **Bound emulated degrees.** In poulpy-cpu-avx and poulpy-cpu-avx512 a registration whose cost grows with the degree takes `crate::tests::bounded_emulation_params(TestParams { .. }, cap)` (cap 256 for HAL-macro registrations, core functions registered through a HAL macro included, 64 for core and parity suites), which clamps `size` and `n` only under `POULPY_TEST_EMULATED=1` (statistical sampling suites and named large-ring suites excepted, registrations at or below the cap needing none), and one above the caps is native-only under a name an emulated `--skip` matches (`ntt_n<degree>`; in poulpy-cpu-avx512 also the listed `core_parity_<family>_fused` modules, `vec_znx_dft_large` and `*_streaming`) or the diff adds a skip entry, emulated large-ring coverage coming from focused cases in the emulated filter list (`core_emulated_tensor`).
- **The emulated BLAS group.** BLAS variant modules carry the suffixes the emulated AVX-512 BLAS group excludes (`rayon`, `_quad`, `_rank2`, `_base2k54`, `_n32`, plus `::concurrency`), every twin test module of poulpy-cpu-avx and poulpy-cpu-avx512 has `rayon` in its path, and a new variant uses them or extends the skip list.
- **CI-named tests keep their paths.** Tests that ci.yml runs by exact path (`fft64::reim::fft_avx2_fma::tests::fft_ifft_roundtrip_avx2`, `ckks_encoding::tests::fft64_precision_families_coexist_in_one_module`), by the `determinism` token or through the `neon_hal` filters, and filter-named portable tests (`test_znx_normalize`, `conjugate_invariant_embed_convolution`), keep their paths unless the PR updates the workflow.

## 14. Do not report

The owner ruled these out for the CPU backend crates, in addition to `docs/review/workspace.md` section 18 and `docs/review/hal.md` section 12: never report or request them.

- A zmm-width AVX-512 or IFMA lane as too wide, or a narrowing request, on a Zen 4 measurement (section 7).
- Embedding-aware prepares (section 6).
- The NTT prime sets' `MAX_LOG_N = 18` or the raw table tests at `2^18` as dead code (section 5.5).
- The oracle's speed, checked accessors in loops (`docs/review/workspace.md` section 4, hot paths carry no checks) or heap temporaries (section 9).
- A backend type without `*LayoutCompatible` markers (section 5.7).
